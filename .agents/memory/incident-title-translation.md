---
name: Incident title translation (display_title)
description: How non-English incident headlines become clean English advisory titles, and the convergence rule that keeps the backfill from starving.
---

Non-English incident headlines (Bahasa Indonesia from West Papua feeds, plus Arabic/Thai/CJK/Cyrillic) are translated to clean English at ingest and stored on a NULLABLE `incidents.display_title`; the original `title` is ALWAYS preserved. UI prefers `display_title`; English raw titles may fall back, but detected non-English rows without a usable English `display_title` must FAIL CLOSED from every normal API read. Never render “Translation pending”, an “UNTRANSLATED” badge, or any other placeholder as an incident title. Raw/admin review may still inspect the source row. English/unprocessed rows stay NULL.

**Presentation-boundary rule:** keep the original `title` through relevance, classification, language detection, search, natural keys, same-event clustering, signatures and deduplication. Resolve `display_title` only after those decisions, at the final presentation row/card/table/prose boundary; deterministic prose, AI grounding/summary payloads, previews, PDFs and exports all count as presentation. A shared derived dataset may replace `title` on its returned clone only after its analysis is complete, while preserving the source row and `displayTitle`. **Why:** translations can change operational keywords and title-token overlap, so resolving early silently changes which incidents qualify or merge; resolving too late lets raw Bahasa leak through secondary cards, editor payloads or generated prose. **How to apply:** pass both fields through intermediate projections; the server's normal-read gate excludes detected foreign titles until a usable English display title exists, and the shared display-title resolver returns an empty value as defense in depth. Regression coverage must prove raw analysis still admits/clusters translated rows while returned/rendered titles are English. Keep the browser-safe detection mirror synchronized with the ingest marker list; stale mirrors silently defeat this final guard.

Runs as one centralized pass (`runTitleTranslation` in `@workspace/ingest`) called from `runIngestOnce` EARLY — right after strikes/ICC piracy, BEFORE the multi-minute scraper chain (own try/catch, non-fatal) — and from a CLI script (`scrape`/`translate-titles`) — NOT per-scraper. Uses the Replit OpenAI integration (gpt-4o-mini, json_object), mirroring `translateScreen.ts`'s fetch client.

**Ordering rule (autoscale teardown — the prod bug to never reintroduce):** the boot forced ingest is an UNOWNED background task; on an autoscale deployment the instance is torn down once HTTP traffic stops, killing whatever step is still running. The translation pass ORIGINALLY ran LAST (after 7 scrapers + 2 extraction passes + URL resolution) and was repeatedly killed before it ever ran, so prod `display_title` stayed NULL and foreign headlines rendered in Bahasa even though dev was correct and `INGEST_FORCE_VERSION` was bumped. **Why:** late steps are the most likely teardown casualty (the strikes + ICC-piracy passes were moved first for the SAME reason). **How to apply:** translation has NO dependency on the scrapers (it reads rows already in the DB), and it converges across runs, so run it EARLY to drain the existing backlog reliably; this run's freshly-scraped foreign rows just translate on the next boot. Symptom of a teardown kill: deploy logs show the forced run start + the early passes, then stop with NO "title translation pass complete" line and "No deployment logs found" shortly after (instance gone). The `ingest_force_v<N>` marker is only written when the run COMPLETES, so a killed run re-forces on the next boot automatically (no re-bump needed) — but it will keep dying until the slow step is early enough to finish.

**Dedicated early-boot sub-run (the real prod fix):** "early INSIDE runIngestOnce" is NOT early enough — it still sits behind the strikes + ICC-piracy passes, which on prod autoscale are slow enough that teardown hits BEFORE translation (prod logs NEVER showed a `title translation pass complete` line at all). So translation also has its OWN dedicated early-boot sub-run in `ingestScheduler.ts` — `runTitleTranslationOnce()` (in `ingestRunner.ts`), SEQUENCED right after the existing strikes + movement early sub-runs inside the `strikesTimer` IIFE (~`STRIKES_BOOT_DELAY_MS` ≈ 8s after boot, inside the cold-start warm window). **Why:** it mirrors the proven strikes/movement early-boot precedent — the only placement that reliably finishes before teardown. **How to apply:** it shares the SAME `withIngestLock` advisory lock (can only ever skip, never collide/deadlock), commits per row, converges, self-skips with no OpenAI key; default limit 150 newest-first lands the current report's headlines in one boot and the backlog drains over later cold starts. Reaches prod ONLY after republish. A long early run can hold the lock past the 60s boot-forced full-ingest timer → full ingest skips + retries next boot (acceptable, existing retry covers it).

**Same-cadence rule (the follow-on prod bug):** the dedicated early-boot sub-run alone is STILL not enough. It runs once per cold start and only drains the backlog that existed AT boot; foreign rows ingested afterwards — on the recurring `setInterval` `tick("interval")` or during the stale-boot `tick("boot")` catch-up — get no translation until the NEXT cold start, so the 7-day country briefs kept rendering raw Bahasa in prod (confirmed: 19 Papua / 345 total untranslated, 15 Papua inside the window) even though the boot pass logged `translated=150 failed=0`. **Why:** the full-chain translation step sits at the very END (after strikes/ICC-piracy) and is torn down before it runs on autoscale; the recurring timer only called `tick` + movement, never a translate pass. **How to apply:** run a dedicated `translationTick(reason)` (thin wrapper over `runTitleTranslationOnce`) on the SAME cadence as ingest — right after `tick("boot")` catch-up AND after `tick("interval")`, plus the existing boot-early pass. Sequence it AFTER `tick` so freshly-inserted rows are visible. The boot-early and boot-catchup passes are often mutually exclusive (advisory-lock race — the 8s early sequence holds the lock past the 60s boot timer, a pre-existing scheduler flaw), netting ~one translate per cold start + one per warm interval, which still converges. Reaches prod ONLY after republish — no `INGEST_FORCE_VERSION` bump needed (this is a cadence fix, not a re-score).

**Completed-run guarantee:** same-cadence scheduling still leaves a specific gap: `runIngestOnce` translates the old backlog near its start, then its scrapers insert fresh foreign rows. An admin/manual call can complete and return with those new rows untranslated, leaving raw Bahasa visible until the next scheduled cycle. Keep BOTH passes inside the full-run advisory lock: early for backlog/crash recovery, post-ingest for rows created by the run. The dedicated scheduler pass remains recovery for interrupted runs. **Why:** this exact gap repeatedly put fresh West Papua police/shooting headlines on the live map with `display_title=NULL` even though their words already matched the Bahasa detector. **How to apply:** any new path that inserts incidents outside the full runner must either supply `display_title` itself or be followed by the shared translation pass; never diagnose this symptom as a Map rendering bug before checking the production row.

**Backlog-vs-cap note:** the per-pass limit stays 150 (newest-first). A standing global backlog >150 does NOT drain in one pass, and even recent map rows can sit behind more than 150 newer candidates from other topics; never treat `translated=150` as proof that the reported rows changed. Verify the exact rows and run additional bounded passes until they leave the queue. Raising the cap lengthens each run (prod: 150 rows ≈ 220s) and costs more LLM calls — leave it at 150. DEV symptom "5 rows stay stuck": a large same-`created_at` tie-batch + Postgres stable heap order + capped runs means limited runs keep hitting the same front rows; foreground `--limit=40` chunks converge (background/setsid CLI runs get killed — do not retry background).

**Convergence rule (the bug to never reintroduce):** detection must be the SAME predicate in JS (`needsTitleTranslation`) and in the candidate SQL `WHERE`, both built from the shared constants (`NON_LATIN_RANGES`, `INDONESIAN_MARKER_WORDS`). The query selects ONLY rows matching the predicate (`display_title IS NULL AND (title ~ <script> OR title ~* <markers>)`). 
**Why:** an earlier version scanned the newest-N NULL rows then JS-filtered. Permanently-English rows keep `display_title` NULL forever, so a wall of newer English rows starves the per-run limit and older non-English rows are never reached. Putting the predicate in SQL means every fetched row is a genuine candidate that drops out once written, so the backfill converges.
**How to apply:** pass the regex patterns as BOUND PARAMS (not interpolated SQL text) to dodge escaping. Postgres word boundary is `\y` (not `\m`/`\b`); script ranges use the ACTUAL boundary chars in the class, valid in both JS and PG regex.

**Bahasa detection:** Bahasa is Latin/ASCII, so a non-ASCII test misses it — match distinctive function words (`yang`, `dengan`, `untuk`, `tewas`, `ditangkap`, `warga`, …). Ambiguous short ones (para/dari/massa/saat/soal) are excluded to avoid rewriting English. `yang` is the strongest marker but collides with the Korean surname "Yang" — accept the rare 1-in-N cosmetic reword; dropping `yang` would miss most Bahasa.

**Prod backfill:** bump `INGEST_FORCE_VERSION` (in `ingestScheduler.ts`) so the next deploy forces a full ingest whose translation pass backfills existing prod rows; convergent ingest passes finish the rest. Dev backfill: run the CLI script with `--commit`.
