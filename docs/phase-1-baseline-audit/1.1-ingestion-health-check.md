## Scheduler architecture (from code)

```
Boot (60s delay) → stale check → runIngestOnce()  [advisory lock]
Timer every INGEST_INTERVAL_HOURS → same path
Early strikes-only boot (8s delay) → runStrikesOnce()  [shares lock]
INGEST_FORCE_VERSION=19 → one forced full ingest per deploy regardless of freshness
```

## Prod SQL — freshness & scheduler markers

Run on prod (read replica OK):

```sql
-- Newest incident per topic (staleness)
SELECT topic, max(occurred_at) AS newest, max(created_at) AS last_inserted, count(*) AS total
FROM incidents
GROUP BY topic
ORDER BY newest DESC NULLS LAST;

-- Forced-ingest marker (did last deploy's boot ingest finish?)
SELECT key, applied_at FROM app_migration_markers
WHERE key LIKE 'ingest_force_v%'
ORDER BY applied_at DESC;

-- Source Health — feeds needing action (effective status)
SELECT topic, name, status, consecutive_failures,
       last_success_at, last_failure_at, left(error_message, 80) AS err
FROM sources
WHERE status = 'failing'
   OR (last_failure_at > last_success_at AND status = 'operational')
ORDER BY topic, name;
```

## Known operational risks (document, not blockers)

1. **Autoscale CPU freeze** — post-listen boot ingest and `setInterval` timers may not complete on Cloud Run without sustained traffic. Forced ingest marker absent = boot chain never finished.
2. **Google News prod IP throttling** — ~20+ feeds timeout on prod egress; dev may look healthy while prod Source Health shows failures.
3. **Client disconnect kills in-request ingest** — `curl --max-time` shorter than full run (~5+ min) aborts mid-chain; market prices often lost last.
4. **Memory note drift** — older docs say "no scheduler"; current code has `startIngestScheduler()` in api-server. Trust `ingestScheduler.ts`.
